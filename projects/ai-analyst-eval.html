Can I Trust the AI Analyst?

Companies want AI that answers business questions straight from the data warehouse. I built a warehouse, wrote questions with checked answer keys, and tested whether small AI models get the numbers right. I also tested whether a semantic layer, where metric definitions are written down once, makes them more trustworthy.

Tools
dbt · DuckDB · MetricFlow · Python
Models
qwen2.5-coder 3B · llama3.2 3B · gemma3 4B
Data
Olist e-commerce · ~100k orders
Timeline
Fall 2026
The setup

A warehouse, 60 questions, three ways to ask

I loaded the Olist Brazilian e-commerce data into DuckDB and modeled it with dbt into clean order, item, customer and seller tables, with 58 data tests. Then I wrote down 18 business metrics in a MetricFlow semantic layer. For example, GMV leaves out canceled and unavailable orders, because it should measure what was actually sold.

Every question has an answer key: a SQL query that was run and checked. Questions come in five types: simple lookups, joins, time questions, metric definitions, and unanswerable questions the data can't support, like "marketing cost per new customer."

The rule for grading

Forgive the formatting, never the analysis. A missing schema name or a different date format still counts. A number that's off by more than 0.1% doesn't. The definition traps are only about 0.7% apart, so a looser grader would miss them.

A · Schema only

The model sees table and column names and writes SQL.

B · Schema + docs

Same, plus a plain-English description of every column.

C · Semantic layer

No SQL at all. The model picks from the list of defined metrics, and MetricFlow writes the query.

Where definitions matter, the semantic layer wins for every model

On questions like average order value or GMV, the SQL usually forgot to leave out canceled orders. That's a small mistake that looks believable: 158.37 instead of 159.77. Through the semantic layer, the filter is part of the metric, so the model can't forget it. It was the one result that held for all three models.

Most of the other gaps could be noise, and I say so

With 60 questions, each score is uncertain by about ±12 points. For qwen, the semantic layer gain is real: the interval doesn't cross zero. For llama and gemma, C scored lower, but the intervals cross zero, so I can't say it made them worse. A semantic layer only helps a model that can use it

The semantic layer trades flexibility for safety. Simple lookups like "how many sellers are there?" dropped from 83% to 33% for qwen, because there was no metric to pick. The weaker models also struggled with the request format. MetricFlow rejected about a third of llama's requests, and llama copied the example from the prompt into its answers. It filtered to the state of Rio de Janeiro in 14 answers when only one question asked about it.

Asked the impossible, models invent an answer

There's no marketing data, but asked for "marketing cost per new customer," the SQL divided freight cost by customers and named the column marketing_cost_per_new_customer. A confident wrong answer with a believable name is the most dangerous kind. Column docs didn't stop it. A closed list of metrics stopped it for qwen in 7 of 12 cases. llama and gemma never refused a single impossible question.

05

I had to check my own grader, twice

The first scores were wrong. The grader marked 9 right answers wrong because the key held extra columns. Later, a semantic-layer request written as items_sold DESC instead of -items_sold was rejected. Fixing that showed the opposite bug: an unsorted list of every state passed because the right one happened to come first. Every fix re-scored the saved answers, with no new model calls, and a self-test answering with the keys still scores 100%.

For a data team lead

When to trust the AI analyst

If I were deciding whether a team should let a small model answer business questions, this is what the results tell me.

Put definitions in a semantic layer

Anything with a business rule (revenue, AOV, cancellation rate) should come from a defined metric, not freshly written SQL. That's where raw SQL failed most and the semantic layer helped every model.

Know what it can't answer

A semantic layer only covers the metrics you define. Questions outside it fail or get forced into the wrong metric. Track which questions people ask, and add metrics for the common ones.

Keep a human on new numbers

Small models rarely say "I can't answer that." Any number headed for a decision should show the query behind it, and someone should check it the first time.

The model choice mattered less than where the business logic lives. A good model with a semantic layer was the only setup I'd trust, and only for questions the layer covers.

Being honest about it

Limits of this study

  • 60 questions, not 100. I planned 100. Sixty were enough for confidence intervals to separate the main effects, and the rest are the next version.
  • Small local models only. Everything ran free on an 8 GB laptop, so the models are 3–4 billion parameters. Larger models would likely score higher in every condition. The question is whether the gaps between conditions would hold.
  • One prompt per condition. The same prompt went to every model, which keeps the comparison fair. But llama copying the example shows that prompt wording affects the scores.
  • One run per answer. Temperature 0 and a fixed seed make runs repeatable, but they don't show how much answers would vary.
