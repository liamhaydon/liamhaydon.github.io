Contoso Retail Analytics

Contoso is a fictional global electronics retailer. Its sales data covers four years (2021–2024) of orders from physical stores and an online store. I used SQL to answer the questions a sales manager would ask, then built a Power BI report so non-technical people can explore the answers themselves.

The brief

Business questions

I started from questions a retail manager would actually ask, not from the tables. Each one maps to a query or a report page below.

  1. What are our top-selling products in each category, and how much of their category do they account for?
  2. Who are our repeat customers, and are they worth more than one-time buyers?
  3. How have monthly sales and profit changed from 2021 to 2024?
  4. Which product categories are the most profitable?
  5. How long do online customers wait for delivery?
Data model

A star schema

The data is organised as a star schema: one central fact table of transactions, surrounded by dimension tables that describe the who, what and where of each sale.

  • factSales: one row per order line (a product within an order). It holds the numbers: Quantity, NetPrice, UnitCost, and the order and delivery dates.
  • dimProduct: product name, brand and category.
  • dimCustomer: customer name, age, gender and location.
  • dimStore: store country, size and open/close dates.

Each dimension joins to the fact table on a key (ProductKey, CustomerKey, StoreKey) in a one-to-many relationship. The same structure drives both my SQL joins and the Power BI model.

Metric definitions used throughout:
Revenue = Quantity × NetPrice  ·  Profit = Quantity × (NetPrice − UnitCost)  ·  Margin = Profit ÷ Revenue
SQL

Three queries, three answers

Written in T-SQL (SQL Server). Each query is also in the sql/ folder of this site's repository.

Q1

Top 3 products by revenue in every category

The Power BI report ranks products by volume. A manager also needs to know which products bring in the most money, and whether one product dominates its category. "Top N per group" is a classic problem: a plain ORDER BY … TOP 3 gives the top 3 overall, not the top 3 per category. 

WITH product_revenue AS (
    SELECT
        p.CategoryName,
        p.ProductName,
        SUM(s.Quantity * s.NetPrice)                AS Revenue,
        SUM(s.Quantity * (s.NetPrice - s.UnitCost)) AS Profit
    FROM factSales  AS s
    JOIN dimProduct AS p
        ON p.ProductKey = s.ProductKey
    GROUP BY p.CategoryName, p.ProductName
),
ranked AS (
    SELECT
        CategoryName,
        ProductName,
        Revenue,
        Profit,
        RANK() OVER (PARTITION BY CategoryName ORDER BY Revenue DESC) AS RankInCategory,
        SUM(Revenue) OVER (PARTITION BY CategoryName)                AS CategoryRevenue
    FROM product_revenue
)
SELECT
    CategoryName,
    RankInCategory,
    ProductName,
    ROUND(Revenue, 0)                           AS Revenue,
    ROUND(100.0 * Profit  / Revenue, 1)         AS MarginPct,
    ROUND(100.0 * Revenue / CategoryRevenue, 1) AS PctOfCategory
FROM ranked
WHERE RankInCategory <= 3
ORDER BY CategoryName, RankInCategory;

How it works

  1. product_revenue CTE: joins each sale to its product, then GROUP BY category + product collapses thousands of order lines into one row per product with its total revenue and profit.
  2. RANK() OVER (PARTITION BY CategoryName …): a window function that restarts the ranking at 1 for every category, ordered by revenue from high to low. Unlike GROUP BY, it keeps every row.
  3. SUM(Revenue) OVER (PARTITION BY CategoryName): puts the category total next to every product row, so I can work out each product's share without a second join.
  4. Final SELECT: keeps ranks 1–3. The filter has to go in the outer query because SQL evaluates WHERE before window functions, so WHERE RANK() … isn't allowed.
  • CTE
  • INNER JOIN
  • GROUP BY
  • RANK()
  • PARTITION BY
  • windowed SUM

Q2

Repeat vs. one-time customers

My Power BI report shows 74 repeat customers generating $319K. This query checks those numbers independently and adds context: what share of total revenue do repeat customers bring in, and do they spend more per order? 

WITH customer_orders AS (
    SELECT
        CustomerKey,
        COUNT(DISTINCT OrderKey) AS Orders,
        SUM(Quantity * NetPrice) AS Revenue
    FROM factSales
    GROUP BY CustomerKey
),
segmented AS (
    SELECT
        CustomerKey,
        Orders,
        Revenue,
        CASE WHEN Orders > 1 THEN 'Repeat' ELSE 'One-time' END AS Segment
    FROM customer_orders
)
SELECT
    Segment,
    COUNT(*)                                                   AS Customers,
    SUM(Orders)                                                AS Orders,
    ROUND(SUM(Revenue), 0)                                     AS Revenue,
    ROUND(SUM(Revenue) / SUM(Orders), 2)                       AS AvgOrderValue,
    ROUND(100.0 * SUM(Revenue) / SUM(SUM(Revenue)) OVER (), 1) AS PctOfTotalRevenue
FROM segmented
GROUP BY Segment
ORDER BY Revenue DESC;

How it works

  1. COUNT(DISTINCT OrderKey): factSales has one row per order line, so one order with 3 products is 3 rows. Counting distinct order keys gives true orders, not lines. This is the most important detail in the query.
  2. CASE WHEN: labels each customer "Repeat" (more than one order) or "One-time".
  3. Second GROUP BY: rolls customers up into the two segments, with average order value = revenue ÷ orders.
  4. SUM(SUM(Revenue)) OVER (): a window function wrapped around an aggregate. The inner SUM is each segment's revenue. The outer SUM … OVER () adds those together across all segments, which gives the grand total for the percentage.
  • COUNT(DISTINCT)
  • CASE
  • chained CTEs
  • aggregate inside a window
  • OVER ()

Q3

Monthly sales, profit and year-over-year growth

A trend line only shows whether sales went up or down. Year-over-year (YoY) growth compares each month with the same month last year, which removes seasonality (December is always bigger than February). The year-to-date running total shows progress toward annual goals. 

WITH monthly AS (
    SELECT
        YEAR(OrderDate)                       AS OrderYear,
        MONTH(OrderDate)                      AS OrderMonth,
        SUM(Quantity * NetPrice)              AS Revenue,
        SUM(Quantity * (NetPrice - UnitCost)) AS Profit
    FROM factSales
    WHERE OrderDate >= '2021-01-01' AND OrderDate < '2025-01-01'
    GROUP BY YEAR(OrderDate), MONTH(OrderDate)
),
with_prior AS (
    SELECT
        *,
        LAG(Revenue) OVER (PARTITION BY OrderMonth ORDER BY OrderYear) AS RevenueLastYear
    FROM monthly
)
SELECT
    OrderYear,
    OrderMonth,
    ROUND(Revenue, 0)                                       AS Revenue,
    ROUND(Profit, 0)                                        AS Profit,
    ROUND(100.0 * Profit / Revenue, 1)                      AS MarginPct,
    ROUND(100.0 * (Revenue - RevenueLastYear)
                / NULLIF(RevenueLastYear, 0), 1)            AS YoYGrowthPct,
    ROUND(SUM(Revenue) OVER (PARTITION BY OrderYear
                             ORDER BY OrderMonth
                             ROWS UNBOUNDED PRECEDING), 0)  AS YTDRevenue
FROM with_prior
ORDER BY OrderYear, OrderMonth;

How it works

  1. monthly CTE: groups sales by year and month. The date filter uses >= start AND < next-year instead of BETWEEN so it can't miss orders late on Dec 31 if the column stores a time.
  2. LAG(Revenue) OVER (PARTITION BY OrderMonth ORDER BY OrderYear): within each calendar month (all the Januarys, all the Februarys…), it looks back one row, which is the same month last year. Partitioning by month is safer than LAG(Revenue, 12), which would give wrong answers if any month had no sales.
  3. NULLIF(RevenueLastYear, 0): prevents a divide-by-zero error. 2021 has no prior year, so its growth comes back NULL rather than a misleading number.
  4. ROWS UNBOUNDED PRECEDING: a running total that restarts each year (PARTITION BY OrderYear) and adds up every month from January through the current row.
  • date functions
  • LAG()
  • NULLIF
  • running total
  • window frame

Reflection

What I learned

Know the grain

The fact table is one row per order line, not per order. Mixing those up silently overcounts orders. COUNT(DISTINCT OrderKey) fixes it.

Window functions > self-joins

Ranking, prior-year comparisons and running totals all became one line each with OVER (…), instead of extra joins or subqueries.

Cross-check your tools

Rebuilding a Power BI number in SQL is a quick way to catch a wrong DAX measure or relationship before a stakeholder does.
